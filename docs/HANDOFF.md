## 1. Product and goals

### 1.1 One paragraph

Tally links a bank account (mocked), tracks spending like a normal budgeting app, and maps every merchant to its parent company and to third-party ratings on Climate, Labor, Governance, Political spending and Privacy (illustrative data). The user picks values, either predefined or typed in their own words, and sets how much each matters on a slider (Nice to have / Important / Dealbreaker). The app labels each merchant **Aligned, Mixed, Conflicts or Unknown** using deterministic rules, shows the evidence behind every label (source, date, scope), suggests alternatives within the user's price budget, and lets the user set a spending goal.

### 1.2 Product principles (non-negotiable)

1. **Evidence, not verdicts.** Every flag shows source, date and scope (merchant or parent company). Stale ratings (older than 18 months) get a "Stale" tag.
2. **The user defines "aligned".** Labels come from the user's own values and importance.
3. **Unknown is never shown as Aligned.** Missing data is shown as Unknown and kept out of the aligned percentage.
4. **"Keep it" is as prominent as "Find alternatives".** Same component, same size, same weight.
5. **Calm, non-judgmental tone.** Second person, short. Never use "bad", "harm", "guilty" or "shame". Use "falls short on", "against your preference", "flagged because you said". No em dashes in UI copy.
6. **Honest about data.** The footer says "Ratings are illustrative demo data." Alternatives are fictional.

### 1.3 Audience and context

The demo is presented live at a hackathon, often on a projector. Above 500px wide it renders inside a centered phone frame. A presenter panel and keyboard shortcuts let the presenter jump between steps and reset quickly. The full demo script must run in under 3 minutes with no API key.

## 6. Architecture

### 6.1 Rendering model

- **Client-rendered app inside a server layout.** `app/layout.tsx` is a server component that loads fonts and renders `<AppShell>`. `AppShell` is a client component that uses `useSyncExternalStore` to detect mount. **Before mount it renders only a "Tally" wordmark splash.** After mount it renders the page, the overlays and the toast host.
  - Why: state lives in localStorage (zustand `persist`), so server HTML can't know it. Gating avoids hydration mismatches. The splash also gives Lighthouse a first paint; without it, headless Lighthouse failed with `NO_FCP`.
  - Consequence: pages can read `window` during render (they never run on the server). `spending/page.tsx` relies on this to read `?filter=` in a `useState` initializer.
- **Phone frame:** `#phone` in `AppShell` is `position: relative; overflow: hidden`. On mobile it's full viewport (`h-dvh`). Above 500px it's 390×844 with radius 44, a hairline border and a shadow, centered on cream, and `useFrameScale` scales it down to fit short windows (projectors).
  - **All overlays (sheets, scrim, toast, tab bar) use `position: absolute` inside the frame, never `fixed`.** Keep it that way or they'll escape the frame on desktop.
- **Screens** use `<Screen>`: an absolutely positioned column with a scrolling `<main>` (24px side padding, safe-area top) and an optional pinned footer for onboarding CTAs (24px above bottom + safe area). Pass `tabs` to leave room for the tab bar (`--tabbar-h: 72px`).

### 6.2 Routing and transitions

- Route groups: `(onboarding)` and `(tabs)`. Each group has a `template.tsx` that re-mounts on navigation to animate **enter** only: a horizontal slide plus fade for onboarding, a crossfade for tabs. There are no exit animations between routes; App Router doesn't support them simply.
- `(tabs)/layout.tsx` redirects to `/start` when `onboarded` is false, and renders the `TabBar`, which persists across tab changes.
- `/report` lives in the tabs group. The Home tab stays highlighted there (`TabBar` matches `/home` and `/report`).
- `/` redirects client-side based on `onboarded`.

### 6.3 State

Two stores in `lib/store.ts`.

**`useApp` (persisted to localStorage key `tally-demo-v2`):**

| Field | Meaning |
|---|---|
| `name` | First name from `/start` |
| `selectedIds` | Ids of selected values, catalog or custom, in display order |
| `customs` | Custom preferences created in the Add sheet (no importance) |
| `importance` | `Record<id, "nice" \| "important" \| "dealbreaker">` |
| `maxPriceIncreasePct` | `0 \| 5 \| 10 \| 20`, default 5 |
| `mode` | `"values"` or `"generic"` (values skipped) |
| `onboarded` | Set when the loading screen finishes |
| `kept` | Merchant ids the user chose to "Keep" |
| `goal` | `Goal \| null` |
| `aiMode` | `"live" \| "scripted"`. Default `live`; the server silently uses scripted when there's no key |
| `lastSeen` | `Snapshot` `{pct, conflicts, flagged}` the user last saw on Home; count-ups start from here |
| `changeBaseline` | Snapshot from before the latest values change; drives "since you changed your values" |

Actions: `set`, `toggleValue`, `addCustom`, `setImportance`, `keep`, `fillPersona(labor = "important")`, `reset` (keeps `aiMode`).

- **If you change the persisted shape, bump the storage key** (`tally-demo-v3`), or old browsers will hydrate stale fields.
- `?fill=maya` is handled at module load at the bottom of `store.ts`. It runs before the first render, so the tabs guard doesn't bounce to `/start`.

**`useUI` (not persisted):** `sheet` (which bottom sheet is open), `toast`, `pulseIds` (rows to pulse on Spending), `reportTab` (`october | november`), `spendingFilter` (`all | flagged | unknown`), plus `openSheet`, `closeSheet`, `showToast`, `hideToast`.

**Derived data:** `buildProfile(state)` turns store fields into an engine `Profile` (generic mode gives an empty preference list). `useProfile()` memoizes it. `useDerived()` returns `{ profile, summary, results (LabelResult per merchant), flagIds, rows (merchants sorted by spend), coverage, generic, spend, kept }`. Screens should read from `useDerived()`, not call the engine directly.

### 6.4 Values changes and recompute

`lib/notify.ts → changeValues(mutate, fallbackText)` is the single path for changing values on the Values tab and in the Add sheet when opened from it:

1. `applyValuesChange` (store) builds the profile before the change, runs `mutate`, builds it after, and computes `changedMerchants`.
2. If anything changed, it sets `changeBaseline = lastSeen ?? snapshot(before)`.
3. It shows a toast: `"N merchants changed"` with a **View** action. View sets `pulseIds` and `spendingFilter = "flagged"`, then navigates to `/spending?filter=flagged`, where the changed rows pulse royal-tint for about 2s. If nothing changed: `"<fallbackText>. No labels changed."`
4. It pre-warms the Amazon explanation in the background (`prewarmAmazon`).

The slider commits only on pointer release (or a key press), so one drag gives one recompute and one toast.

### 6.5 Overlays

`Overlays.tsx` maps `useUI.sheet` to a component inside `<BottomSheet>`, wrapped in `AnimatePresence`. Sheet types: `merchant {id}`, `goal {merchantId}`, `add`, `settings`, `demo`, `howcalc`, `bank`. Only one sheet is open at a time. Opening the goal sheet from the merchant sheet replaces it.

`BottomSheet` gives you: a scrim (black/40, tap to close), a spring-in panel, drag-to-dismiss **from the grabber only** (`dragControls`, `dragListener={false}`) so inner content can scroll, Escape to close, and focus moved in and restored on close.

## 7. Domain model (`lib/types.ts`)

```ts
type Issue = 'climate' | 'labor' | 'governance' | 'political' | 'privacy';
type Importance = 'nice' | 'important' | 'dealbreaker';
type Rating = { issue; score /*0–100*/; source; date /*YYYY-MM*/; scope: 'merchant' | 'parent'; url };
type Merchant = { id; name; parentId; category; tags: string[]; ratings: Rating[] };
type Parent = { id; name };
type Transaction = { id; date; rawName; amount; merchantId?; excluded? };
type PreferenceRule =
  | { kind: 'rating'; issue: Issue }
  | { kind: 'attribute'; tag: string; polarity: 'avoid' | 'prefer'; alsoTags?: string[] }
  | { kind: 'entity'; parentId: string; polarity: 'avoid' };
type Preference = { id; label; sourceText?; type: 'rating'|'attribute'|'entity'|'unsupported'; rule?; importance; clarifications?: {q,a}[] };
type Profile = { name; preferences: Preference[]; maxPriceIncreasePct: 0|5|10|20 };
type Alternative = { forMerchantId; name; availability: 'national'|'regional'|'online'; priceDeltaPct; tags; ratings };
type Goal = { id; label; merchantIds; baseline; target };
type Label = 'Aligned' | 'Mixed' | 'Conflicts' | 'Unknown';
type Evaluation = 'pass' | 'fail' | 'unknown' | 'na';
type GenericSummary = 'Unrated' | 'Weak' | 'Strong' | 'Mixed';
```

Two additions beyond the original brief: `privacy` in `Issue`, and `alsoTags` on attribute rules (used when the user says fast casual counts as fast food).

## 8. Rules engine (`lib/engine.ts`)

Pure functions, no AI, fully unit tested. Constants: `PASS_SCORE = 50`, `FAR_SCORE = 30`, `STALE_MONTHS = 18`.

### 8.1 `evaluate(merchant, pref) → 'pass' | 'fail' | 'unknown' | 'na'`

- **rating:** no rating for the issue → `unknown`; score < 50 → `fail`; else `pass`.
- **attribute avoid:** the merchant has the tag (or any `alsoTags`) → `fail`; else `pass`.
- **attribute prefer:** has the tag → `pass` ("supports your value"); else `na`. Prefer-rules never fail.
- **entity avoid:** `merchant.parentId === rule.parentId` → `fail`; else `pass`.
- **unsupported** (or no rule) → `na`.

`isFarBelow(merchant, pref)`: true for a rating rule whose score is < 30.

### 8.2 `label(merchant, profile) → LabelResult`

First match wins:

1. Any **fail on a Dealbreaker**, or a **far-below fail (score < 30) on an Important** rating value → **Conflicts**
2. Any **unknown on an Important or Dealbreaker** → **Unknown**
3. Any **fail on an Important** → **Mixed**
4. Otherwise → **Aligned**

- Nice-to-have never changes the label. A Nice fail adds to `notes` (shown in ink-3 in the merchant sheet). A Nice unknown is ignored.
- A merchant that isn't in the data (`undefined`) → Unknown.
- Attribute and entity rules have no "far below" tier: Important → Mixed, Dealbreaker → Conflicts.

`LabelResult = { label, reasons: Preference[], notes, supports /*prefer-rules satisfied*/, severe /*Important values that fell far short*/ }`.

`reasonText(result)` builds the reasons line:
- Dealbreaker: "Flagged because you marked Worker treatment as a dealbreaker."
- Far below: "Flagged because it falls far short on Climate, which you marked as important."
- Both: the dealbreaker sentence + "It also falls far short on X."
- Mixed: "Flagged because you marked X as important."
- Unknown: "No reliable rating yet for X, which you marked as important."

### 8.3 Summary, flags and changes

- `spendByMerchant(txs)`: excludes `excluded` transactions; unmapped ones are keyed `unmapped:<rawName>`.
- `summarize(txs, merchantsById, profile)` → `{ total, aligned, mixed, conflicts, unknown, labeled, alignmentPct, coveragePct, enoughData, labels }`:
  - `labeled = aligned + mixed + conflicts`; `unknown` = Unknown + unmapped spend
  - `alignmentPct = round(aligned / labeled × 100)`
  - `coveragePct = round(labeled / total × 100)`
  - `alignmentPct` is `null` when coverage < 20%; the UI shows "Not enough data yet"
- `flags(txs, merchantsById, profile, kept)`: Conflicts by spend (desc), then Mixed by spend (desc), **excluding kept**. "Keep it" removes a merchant from flags but **not** from the percentage.
- `changedMerchants(txs, merchantsById, before, after)`: ids whose label differs.
- **Generic mode** (values skipped): `genericSummary(m)` gives a one-word rating summary per merchant: Unrated (no ratings), Weak (any score < 40), Strong (all ≥ 60), else Mixed. `ratedCoverage` gives the "76% of your spending matched to rated companies" number.

### 8.4 Alternatives

`alternativesFor(merchantId, alternatives, profile)` → `{ fits, overBudgetCount }`:
- **fits** = same `forMerchantId`, `priceDeltaPct <= maxPriceIncreasePct`, **and** labels Aligned under the current profile (`alternativeAsMerchant` turns it into a Merchant for evaluation).
- **overBudgetCount** = alternatives for that merchant with `priceDeltaPct > maxPriceIncreasePct`.

### 8.5 Helpers

`formatRatingDate("2026-03") → "Mar 2026"`, `isStale(rating, today="2026-10-30")` (> 18 months), `profileHash(profile)` (stable djb2 hash of budget + `[id, rule, importance]`, used for explanation caching), `round2`.

## 11. AI layer

### 11.1 Principles

- AI only (a) parses a free-text value into a structured preference and (b) writes a 2–3 sentence explanation. **It never computes labels, totals or ratings.**
- Every AI response is validated. Any failure falls back silently.
- Processing moments always last **at least 900ms** (`MIN_PROCESSING_MS`), so scripted mode feels the same as live.

### 11.2 `POST /api/parse-preference`

Input (zod `ParseInputSchema`): `{ text (1–500 chars), history: {q,a}[] (max 4), mode: 'live'|'scripted' }`.

Output: one of
- `{ status:'clarify', question, options[2..4], progress?: {step,total} }`
- `{ status:'result', preference:{id,label,sourceText,type,rule,clarifications}, summary, basis }`, where basis ∈ "Based on merchant category" | "Based on company ratings" | "Based on who owns the company"
- `{ status:'unsupported', label, message }`
- `{ status:'declined', message }`
- `{ status:'failed', message }`: the generic fallback, not from the model

Each response also carries `source`: `rule` | `scripted` | `live` | `fallback`.

Flow:
1. **Identity guard first, in every mode:** `isIdentityAvoidance(text)` (a group word + an ownership word + an avoidance word) → `declined` with "We can help you support businesses, like women-owned or immigrant-owned. We don't filter businesses out based on who owns them."
2. `mode === 'scripted'` or no key → `scriptedParse(text, history) ?? FAILED`.
3. Live: `complete(PARSE_SYSTEM, JSON.stringify({text, history}))` → `extractJson` → `ParseOutputSchema.parse`. A clarify after 2 answered questions is rejected. Results get `id = custom-<slug(label)>`, `sourceText`, `clarifications`.
4. Any error (timeout, API error, bad JSON, failed validation) → scripted for known inputs, else `FAILED` ("We couldn't read that. Try rephrasing or pick from the list.").

Scripted inputs (`lib/ai/scripted.ts`):

| Input contains | Response |
|---|---|
| "fast food" | Clarify "Does fast casual like Chipotle count?" [Yes, No] → **No**: `FAST_FOOD_PREF` (attribute `fast_food` avoid, label "Avoid fast-food chains", basis category). **Yes**: the same plus `alsoTags: ['fast_casual']` |
| "amazon" | Result: entity `amazon` avoid, "Avoid Amazon", summary "Also covers Whole Foods (owned by Amazon).", basis owner |
| "politic" | Q1 "What do you mean by political association?" [3 options, progress 1 of 2] → Q2 "Which counts?" [Corporate PAC, Executive donations, Trade groups] (2 of 2) → result rating `political` |
| "parental leave" | Unsupported "Parental leave", "We can't track this yet. We've saved it and will tell you when we have reliable data." |
| identity-based avoidance | Declined (see above) |
| anything else | `null` → `FAILED` |

### 11.3 `POST /api/explain`

Input (zod `ExplainInputSchema`): `{ cacheKey, mode, merchant:{id,name,category,parentName,differentParent}, ratings[], label, reasons:[{label,importance,rule,severe?}], notes:[...], profile:{preferences:[{label,importance}]} }`. Built client-side by `buildExplainInput`.

- **Unknown, or no ratings** → fixed text, no AI: "There isn't enough reliable evidence to recommend a change here."
- Otherwise: compute `templateExplain(input)`. In live mode with a key, call Claude with `EXPLAIN_SYSTEM`, collapse whitespace, and accept the result only if `isValidExplanation` passes: it names a source and a date, has 2–4 sentences, is at most 600 chars, has no em dash and none of the banned words. Otherwise use the template.
- The template always cites `the <Source> (<Mon YYYY>)` and ends with one caveat: stale (> 18 months) → "Part of this evidence is more than 18 months old…"; parent scope with a different parent → "This reflects the parent company, not this store."; parent scope, same company → "This reflects the company as a whole, not one store or service."; else "These ratings are illustrative and may change…".
- **Caching:** server-side per-instance `Map` keyed `mode:cacheKey`. Client-side `Map` keyed `mode:merchantId:profileHash`, plus in-flight de-duplication. `prewarmAmazon()` runs after every values change.

### 11.4 Model call (`lib/ai/claude.ts`)

```ts
client.messages.create(
  { model: process.env.ANTHROPIC_MODEL || "claude-haiku-5-5", max_tokens, system, messages:[{role:"user", content}],
    output_config: { effort: "low" } },
  { timeout: 6000, maxRetries: 0 });
```

`stop_reason === "refusal"` and empty text are treated as errors, which triggers the fallback.

## 18. Conventions for making changes

- **Change logic in the engine, not in components.** Screens read `useDerived()`. Keep `lib/engine.ts` pure, and add a test for any rule change.
- **Changing data:** edit `ROWS` in `data/merchants.ts` (or the transaction rows), then run `npm test`. If numbers move, update `tests/engine.test.ts`, the README demo script, the golden numbers (section 10) and the scenario table (section 9.2), and `BEFORE` in `lib/demo.ts` (the Home-after-Dealbreaker snapshot).
- **Changing persisted state shape:** bump the `persist` key in `lib/store.ts`.
- **Changing AI contracts:** update the zod schemas, the prompts, the scripted responses and `tests/ai.test.ts` together. Never let model output decide a label.
- **New UI:** use the tokens and `components/ui`; keep overlays `absolute` inside `#phone`; add `whileTap={{ scale: 0.98 }}` to tappables; keep tap targets ≥ 44px; follow the copy rules; check contrast (section 14.4).
- **Next.js 16:** read `node_modules/next/dist/docs/` before using framework APIs you haven't used in this repo. `cacheComponents` is off on purpose.
- **Before handing back:** `npm run lint && npm run typecheck && npm test && npm run build`, then click through the demo script (section 13).
- **Git:** work on a branch; there's no remote yet. Commit trailers used so far: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
